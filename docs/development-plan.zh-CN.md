## 1. 计划说明

本计划将需求文档中的阶段 0 至阶段 4 转换为可执行的开发工作。时间按 **2 名核心开发者 + 兼职安全/文档支持**估算，采用两周一个迭代；每个阶段结束必须有可运行版本、测试结果和决策记录。

如果由单人开发，建议保留阶段顺序和验收标准，将阶段 1、2 的周期调整为原计划的 1.5 至 2 倍，不要通过减少安全与恢复测试来压缩周期。

### 1.1 角色分工

| 角色 | 主要责任 |
| --- | --- |
| Core Maintainer | 架构、领域模型、配置、存储、发布和代码评审。 |
| Runtime Integrator | Claude Code/Codex Adapter、进程管理、事件/错误映射和兼容矩阵。 |
| Security/Platform（兼职） | Policy、secret、隔离、威胁模型和 CI 安全检查。 |
| Docs/Community（兼职） | 快速开始、示例、迁移说明、用户访谈和 issue triage。 |

### 1.2 统一工程规则

- 每个功能以 issue/PR 交付，必须包含测试或说明为什么无法自动化测试。
- Adapter、配置 schema、事件格式和 CLI 输出均要有版本号或兼容策略。
- 所有 Run 状态变更先写入持久化记录，再通知 CLI/API，避免进程崩溃造成“假成功”。
- 任何新增凭证、网络、目录或命令权限都必须同步更新 Policy、威胁模型和诊断信息。
- 每个迭代最后半天用于集成测试、文档和可回滚发布，不将质量工作挤到阶段末尾。

## 2. 总体排期与发布门槛

| 阶段 | 周期基线 | 版本/里程碑 | 阶段输出 | 进入下一阶段的门槛 |
| --- | --- | --- | --- | --- |
| 阶段 0 | 2-3 周 | `v0.1-spec` | Adapter 契约、数据模型、兼容矩阵、原型 | 两个 Runtime 可完成同一冒烟任务，核心决策冻结。 |
| 阶段 1 | 4-6 周 | `v0.1.0-mvp` | CLI、本地控制面、两个内置 Adapter、隔离和 Run/Session | 新用户 10 分钟内完成首次调用，安全与恢复验收通过。 |
| 阶段 2 | 4-6 周 | `v0.2.0-api` | HTTP API、事件流、路由、Adapter SDK | 自动化调用和第三方 Adapter 契约测试可运行。 |

阶段 4 不是自动开始的开发承诺。若阶段 3 未出现重复的远程执行、组织身份或集中审计需求，应继续加强本地开源核心。

## 3. 阶段 0：技术验证与规格冻结（2-3 周）

### 目标

确认“统一 Adapter”能够覆盖 Claude Code 和 Codex CLI 的真实调用差异，并冻结 MVP 可以长期维护的领域模型、配置和事件边界。

### 周级计划

#### 第 1 周：调研、能力矩阵与架构骨架 `[x]`

- 记录 Claude Code 与 Codex 的安装方式、启动参数、认证来源、交互/非交互模式、退出码、输出格式、session 能力和取消方式。
- 建立能力矩阵：`execute`、`stream_events`、`cancel`、`create_session`、`resume_session`、`healthcheck`，对不支持的能力标记为 `unsupported`。
- 确定核心包边界：`core`、`adapter-contract`、`storage`、`policy`、`cli`，暂不引入 Web UI。
- 选择本地持久化方案和日志格式；优先采用可迁移的 SQLite/JSONL 组合或等价方案，并记录 ADR。
- 输出最小配置 schema、统一错误分类和状态枚举草案。

**产出物**：能力矩阵、架构图、ADR-001（Adapter 边界）、ADR-002（本地存储）、schema 草案、风险清单。

#### 第 2 周：双 Adapter 冒烟原型 `[x]`

- 实现最小 Adapter 接口：版本探测、健康检查、启动一次性任务、读取 stdout/stderr、退出码转换。
- 用真实安装的 Claude Code/Codex 执行同一条只读任务，保存原始输出和统一事件样例。
- 验证进程超时、用户取消、启动失败、二进制不存在和非零退出码等异常路径。
- 验证 session 的最小映射：能恢复则保留原生 ID，不能恢复则返回明确能力状态。
- 建立跨平台路径和 shell 差异记录，至少覆盖当前开发环境与目标 Linux/macOS 环境。

**产出物**：两个最小 Adapter、冒烟测试脚本、原始事件样例、兼容矩阵 v0.1。

#### 第 3 周：规格冻结与实现切片 `[x]`

- 固化 `Runtime/Profile/Project/Policy/Session/Run` 数据模型及字段约束。
- 固化配置合并规则、secret reference 格式、事件 schema、错误码和 Run 状态机。
- 为阶段 1 创建按模块拆分的 issue/PR 列表，标记依赖和验收测试。
- 对 Policy 默认值、数据脱敏和本地 API 暴露面做一次安全评审。

**阶段 0 退出条件**：`[x]` 两个 Adapter 可用同一请求完成冒烟任务；统一状态、错误、原始输出引用可落盘；未决问题均有 owner 和截止日期。

## 4. 阶段 1：MVP 本地统一入口（4-6 周）

### 目标

让个人开发者通过 `agentdock` CLI 注册、诊断并调用 Claude Code/Codex；每次运行都绑定项目、配置、策略和 session，并能在异常后恢复到可解释状态。

### 开发切片

#### 第 1 周：仓库骨架、配置和领域层 `[x]`

- 初始化包管理、代码质量检查、单元测试、集成测试和跨平台 CI。
- 实现配置加载、默认路径、环境变量覆盖、schema 校验和配置版本迁移机制。
- 实现领域实体与状态机：Runtime、Profile、Project、Policy、Session、Run。
- 为每个实体建立稳定 ID、创建/更新时间和软删除/归档字段。
- 先写状态转换表和非法转换测试，再接入真实 Adapter。

**检查点**：空仓库可以通过 `config validate`，非法配置能返回带路径的错误。

#### 第 2 周：Runtime 注册与 Adapter 运行器 `[x]`

- 实现 Runtime 的发现、注册、查看、启用/禁用和健康检查。
- 将阶段 0 的 Claude Code/Codex Adapter 接入统一 Runner，统一处理 stdin、stdout、stderr、退出码、超时和取消。
- 设计子进程生命周期：启动、心跳/输出读取、正常退出、强制终止、残留进程清理。
- 记录 Runtime 版本和 Adapter 版本，执行前做兼容性检查。
- 增加 `runtime list`、`runtime doctor` 等 CLI 命令。

**检查点**：不存在的二进制、版本不匹配和启动超时都能给出可操作诊断。

#### 第 3 周：Profile、Project、Policy 与 Secret Reference `[x]`

- 实现 profile 继承和项目覆盖，定义冲突时的明确优先级。
- 实现工作目录规范化、项目根目录校验、环境变量白名单和敏感键名遮蔽。
- 接入第一种本地 secret 解析方式（环境变量或 OS Keychain），保留 Secret Provider 接口。
- 实现 `run dry-run`：展示最终 runtime、工作目录、策略摘要和环境变量键名，不启动 Agent。
- 对越界目录、未知 secret、禁止网络/命令等情况编写拒绝测试。

**检查点**：两个 Project 的工作目录和允许的环境变量集合互不泄漏；配置文件不出现明文密钥。

#### 第 4 周：Session、Run 存储和事件记录 `[x]`

- 实现 Session 创建、列表、详情、恢复能力标记、归档和删除。
- 实现 Run 创建、排队、运行、成功/失败/取消/超时状态及不可变配置/策略快照。
- 采用追加式事件写入；进程退出前后均记录时间、退出码和原始 runtime 状态。
- 实现崩溃恢复扫描：重启时将没有心跳且进程不存在的 `running` Run 标记为 `failed` 或 `unknown`，并给出原因。
- 实现 `run show`、`run events`、JSON/JSONL 导出。

**检查点**：配置修改后历史 Run 的快照不变；强制终止和进程崩溃不留下永久 `running`。

#### 第 5 周：CLI 完整闭环与文档 `[~]`

- 完成 `runtime`、`profile`、`project`、`session`、`run` 命令及统一退出码。
- 增加交互模式与非交互模式边界；脚本模式禁止彩色和不可解析输出。
- 实现 `agentdock doctor`，覆盖二进制、版本、目录、配置、secret reference 和权限检查。
- 编写快速开始、配置参考、安全边界、故障排查和两个端到端示例。
- 用全新临时用户目录从安装到首次调用走通文档。

**检查点**：新用户在 10 分钟内完成 Runtime 发现、诊断和首次只读任务。

#### 第 6 周（可选）：稳定性、发布与早期试用 `[ ]`

- 补齐 Windows、Linux、macOS 的路径、信号、shell 和权限差异测试。
- 执行长任务、并发提交、取消、磁盘满、日志损坏和升级迁移测试。
- 完成安全评审、依赖漏洞扫描、许可证检查和发布包校验。
- 选取 5-10 名早期用户试用，按阻断级别修复问题。
- 发布 `v0.1.0-mvp`，同步 CHANGELOG、已知限制和兼容矩阵。

**阶段 1 退出条件**：`[~]` P0 本地闭环已可用，关键安全/稳定性、多平台和发布验收仍未全部完成；首次调用已在当前机器通过，早期用户成功率尚未统计。

## 5. 阶段 2：可编程调用与插件化（4-6 周）

### 目标

把 CLI 闭环扩展为稳定的本地 API 和 Adapter 生态入口，让脚本、CI 和第三方 Runtime 可以接入。

### 周级计划

#### 第 1 周：API 与事件协议 `[~]`

- `[x]` 将 Run/Session/Runtime 操作映射为版本化 HTTP API，例如 `/api/v1/runs`。
- `[x]` 固化请求校验、响应错误格式、基础分页、SQLite 幂等键和资源状态字段。
- `[x]` 定义 SSE 事件类型、顺序、重连游标和终态事件。
- `[x]` 默认仅监听回环地址，并拒绝其他监听地址。
- `[x]` 为 API schema 生成 OpenAPI 文档和受认证保护的发现端点 `/api/v1/openapi.json`。

#### 第 2 周：本地 API 服务与认证边界 `[~]`

- `[x]` 实现本地服务启动、健康检查、优雅关闭和端口冲突诊断。
- `[x]` 实现 Run 提交、查询、取消、事件订阅和 Session 列表等 P0 API。
- `[x]` 增加本地 token/进程边界的最小认证方案，禁止日志记录认证信息。
- `[x]` 增加并发限制、请求超时、请求体大小和输出背压处理。
- 用 CLI 作为 API 客户端跑一遍端到端回归。

#### 第 3 周：简单路由与可解释决策 `[~]`

- `[x]` 定义路由输入：所需能力、Project、Policy 要求和 Runtime 健康状态。
- `[x]` 实现显式 Profile 优先；自动路由仅在候选唯一或 Project 默认明确时执行。
- `[x]` 输出路由决策说明并写入 Run 不可变 snapshot：候选、拒绝原因、最终选择和解释。
- `[x]` 对没有可用候选、能力不足、健康异常、歧义和策略冲突编写确定性测试。

#### 第 4 周：Adapter SDK 与 manifest `[~]`

- `[x]` 抽取稳定的 Adapter 接口、类型、事件构造器、错误转换器和测试工具。
- `[x]` 定义 manifest：名称、版本、入口、兼容的 AgentDock API、Runtime 版本范围和所需权限。
- `[x]` 提供确定性的 Echo Adapter 和本地开发模式。
- `[ ]` 实现本地 Adapter 的安装、列出、启用、禁用和卸载；第三方 Adapter 默认不自动获得额外权限。
- `[x]` 建立契约测试辅助函数，验证健康检查、执行、取消、事件和错误路径。

#### 第 5 周：可靠性、数据策略与集成 `[ ]`

- 完善重启恢复、事件游标、重复请求幂等和 Adapter 崩溃处理。
- 实现数据保留期限、日志级别、输出保存开关和脱敏规则。
- 完成 API、CLI、Claude Code/Codex 两个内置 Adapter 和示例第三方 Adapter 的集成测试。
- 编写 API/SDK 迁移指南和兼容矩阵更新流程。

#### 第 6 周（可选）：Beta 发布 `[ ]`

- 运行压力、长连接断开重连、并发取消和异常注入测试。
- 修复 SDK 使用者反馈，冻结 API v1 的破坏性变更规则。
- 发布 `v0.2.0-api`，提供 API 示例项目和 Adapter 开发教程。

**阶段 2 当前退出条件**：`[~]` API 安全边界、跨重启幂等、SSE 生命周期、确定性路由、Adapter SDK 第一切片和 OpenAPI 已完成；本地 Adapter 生命周期、完整跨平台/压力验收仍未完成。

## 6. 阶段 3：团队试点与治理（6-8 周）

### 目标

验证 AgentDock 在小团队和 CI 中的配置共享、审计、策略一致性和可运维性，不提前建设完整企业平台。

### 周级计划

#### 第 1-2 周：项目模板与配置协作

- 定义可提交仓库的项目配置格式，分离公共 profile 与个人 secret reference。
- 实现全局、仓库、用户和 CI 层级的覆盖规则及冲突诊断。
- 增加配置锁定/兼容版本字段，防止团队成员使用未测试 Adapter。
- 提供模板初始化、配置检查和差异预览命令。

#### 第 3 周：只读界面与审计检索

- 根据用户试用反馈选择只读 Web 控制台或 TUI，不开发复杂编辑器。
- 展示 Runtime、Profile、Project、Session、Run、策略事件和错误详情。
- 支持按时间、项目、状态、Runtime 和 Run ID 检索。
- 保持界面调用公开 API，不在界面层复制核心业务逻辑。

#### 第 4 周：CI 非交互模式

- 提供 CI 示例（GitHub Actions/GitLab CI 任选其一作为第一目标）。
- 增加机器可读输出、确定性退出码、超时、取消和 artifacts 导出。
- 支持从 CI secret 注入 Secret Provider 引用，禁止将 secret 写入工作区。
- 对重复提交、构建重试和工作目录清理编写集成测试。

#### 第 5 周：审计、审批与策略报告

- 固化审计事件字段：操作者、来源、项目、Runtime/version、策略快照、结果和关联构件。
- 增加高风险操作的确认/审批钩子，默认不阻塞低风险只读任务。
- 生成策略报告和 Run 摘要，支持脱敏后归档。
- 对审计记录做追加写、防篡改校验和保留策略验证。

#### 第 6 周：试点运行与可运维性

- 选择 3 个独立团队或项目，明确每个试点的任务类型、成功标准和反馈周期。
- 观察首次调用成功率、Adapter 失败率、策略拒绝率、恢复成功率和用户留存。
- 完成升级、回滚、备份恢复、日志轮转和数据迁移演练。
- 建立 issue 分级和响应规则，优先修复数据泄漏、Run 丢失和不可恢复问题。

#### 第 7-8 周（按反馈启用）：收敛与发布

- 根据试点结果砍掉低使用功能，修复阻断问题和文档缺口。
- 完成威胁模型复审、依赖升级和发布安全检查。
- 发布 `v0.3.0-pilot`，给出明确的生产限制和不支持场景。
- 召开阶段评审，决定是否满足阶段 4 启动条件。

**阶段 3 退出条件**：至少 3 个团队完成连续试用；本地与 CI 的策略结果一致；审计记录可从 Run 追溯到 Runtime、版本和策略；无已知高危安全问题。

## 7. 阶段 4：远程执行与企业能力（需求触发后 8-12 周）

### 启动前的验证工作（2 周，不计入实现周期）

- 访谈阶段 3 用户，确认远程 Worker、组织身份、集中审计和配额是否为重复需求。
- 记录数据驻留、网络拓扑、凭证管理、隔离等级和合规要求。
- 以威胁模型和成本模型评估自托管控制面、远程 Worker 和云托管三种方案。
- 只有在至少 3 个独立团队持续使用并提出相同远程需求后，才冻结实现范围。

### 建议的 8-12 周实现顺序

1. **远程 Worker 协议（第 1-3 周）**：定义 Worker 注册、能力心跳、任务租约、事件回传、取消和断线恢复；保留本地 Run 状态机作为唯一事实来源。
2. **身份与权限（第 3-5 周）**：实现组织、项目、角色、Worker 权限和 secret 范围；默认拒绝跨组织和跨项目访问。
3. **集中审计与构件（第 5-7 周）**：实现审计汇聚、输出索引、保留策略、导出和访问记录；不默认集中保存完整提示词或源码。
4. **配额与运维（第 7-9 周）**：增加并发/时长/成本配额、Worker drain、升级、健康检查和故障转移。
5. **安全和试运行（第 9-12 周）**：完成端到端安全测试、断网/重试/重复执行测试、运维手册和有限客户试点。

**阶段 4 退出条件**：远程任务在断线、重试和取消场景下状态可解释；组织权限和 secret 隔离通过评审；有明确的数据驻留、备份和故障恢复说明。

## 8. 跨阶段测试计划

| 测试层级 | 阶段 0 | 阶段 1 | 阶段 2 | 阶段 3 | 阶段 4 |
| --- | --- | --- | --- | --- | --- |
| 单元测试 | 状态/schema 原型 | 核心领域、Policy、存储 | API、路由、SDK | 模板、审计、CI 边界 | 身份、配额、租约 |
| Adapter 契约测试 | 接口草案 | 两个内置 Adapter | 第三方示例 Adapter | 兼容矩阵回归 | Worker/远程 Adapter |
| 集成测试 | 双 Runtime 冒烟 | CLI 到真实 Runtime | API 到 CLI/Adapter | 本地到 CI | 控制面到 Worker |
| 安全测试 | 威胁模型 | secret/越界/日志脱敏 | API 暴露/权限/背压 | 审计完整性/机器身份 | 组织隔离/网络/灾备 |
| 故障注入 | 启动失败/超时 | 崩溃/取消/磁盘满 | 断连/重试/重复请求 | 升级/回滚/备份 | Worker 断网/租约过期 |

每个发布版本至少满足：核心单元测试通过、两个内置 Adapter 集成测试通过、依赖漏洞扫描无未处理高危项、快速开始文档在干净环境验证通过。

## 9. Issue 与里程碑组织

建议按以下 Epic 建立 issue，避免按页面或零散命令拆散领域边界：

- `E0-SPEC`：Runtime 调研、Adapter 契约、ADR、schema、威胁模型。
- `E1-CORE`：领域模型、状态机、配置、存储、事件和恢复。
- `E1-RUNTIME`：Runtime Runner、Claude Code/Codex Adapter、版本探测。
- `E1-SECURITY`：Policy、目录/环境隔离、Secret Reference、脱敏。
- `E1-CLI`：五组 CLI、doctor、导出、脚本模式和文档。
- `E2-API`：HTTP API、SSE/NDJSON、幂等、认证边界和路由。
- `E2-SDK`：Adapter SDK、manifest、脚手架、契约测试。
- `E3-TEAM`：项目模板、CI、审计、只读界面、试点运维。
- `E4-REMOTE`：Worker、组织身份、集中审计、配额和灾备。

每个 issue 应包含：问题背景、依赖 Epic、输入/输出契约、测试场景、风险、验收条件和是否影响兼容性。涉及 schema、API、事件或 Adapter 接口的 PR 必须附迁移说明或明确“无破坏性变更”。

建议里程碑：

1. `M0-spec-freeze`：阶段 0 退出，冻结 P0 数据模型和 Adapter 接口。
2. `M1-local-loop`：阶段 1 核心闭环，先发布候选版本再做早期试用。
3. `M2-programmatic`：阶段 2 API/SDK 稳定，开放第三方 Adapter 示例。
4. `M3-pilot`：阶段 3 团队试点，基于数据决定是否远程化。
5. `M4-remote-go/no-go`：阶段 4 启动评审，不满足条件则明确关闭该里程碑。

## 10. 每周执行节奏

- 周一：确认本周目标、依赖和风险，更新 issue 状态。
- 周二至周四：功能实现与测试；跨模块变更在当天提交小 PR，避免末周堆积。
- 周五：集成回归、文档验证、演示和下一周切片；阶段末周增加安全与发布检查。
- 每两周：输出一个可运行版本和变更记录，不以“代码已合并”作为里程碑完成标准。
- 每阶段结束：召开退出评审，逐项核对验收条件、未决风险、用户反馈和下一阶段 go/no-go。

## 11. 首批开发顺序（立即可执行）

如果现在开始编码，建议按以下顺序建立第一批任务：

1. 建立仓库骨架、许可证、贡献指南、CI 和文档目录。
2. 完成 Claude Code/Codex 的真实调用调研和能力矩阵。
3. 固化 Adapter 最小接口、统一状态/错误/事件类型及其测试样例。
4. 实现本地配置加载和 `Runtime/Profile/Project/Policy/Run/Session` 数据模型。
5. 先实现只读 `dry-run` 和健康检查，再开放真实执行。
6. 接入一个 Runtime 做完整 Run 闭环，再接入第二个 Runtime 做契约验证。
7. 在任何并发、路由或 Web UI 之前，完成 secret 脱敏、目录边界、取消和崩溃恢复测试。
8. 发布可供 5 名早期用户试用的 MVP 候选版本，依据真实失败路径调整阶段 2 设计。

这条顺序的目的，是尽快验证核心控制面是否成立，同时让安全边界、可恢复性和 Adapter 可维护性先于外围功能稳定下来。
